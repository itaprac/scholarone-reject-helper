Cały blok top-level (parsowanie argów, createBrowserSession(), try/catch/finally) → cienki bin/scholarone.js. Workflow stają się funkcjami runX(page, config), które nic nie robią przy imporcie.

Podział

  • src/workflows/ — reject-scan, reject-from-report, screening, reviewers
  • src/steps/ — checklist, reject-email, queue
  • src/reporting/ — report, csv, artifacts

Cel: żaden plik powyżej ~500 linii. Moduły reguł zostają bez zmian.

Testy ścieżki odrzucania

Najgroźniejsza operacja w projekcie (wysyłka maila „Save and Send") nie ma dziś ani jednego testu. Dopisz offline: rozpoznanie checklisty, znalezienie kontrolki reject, wypełnienie maila, rozpoznanie potwierdzenia wysyłki (nie samego zamknięcia popupu), limit --max-rejected.

Te testy napisz PRZED etapem 2 — mają być siatką bezpieczeństwa dla deduplikacji, nie jej efektem ubocznym.

4. Jedna warstwa opcji — ~6 h

Deklaratywna tabela opcji

src/config/options.js: nazwa, flaga CLI, klucz env, typ, min/max, domyślna, tryby, etykieta dla UI. Z niej generuje się parser CLI, walidator, budowanie argów joba, publicConfig(), zapis ustawień i pola formularza.

Nowa opcja = jeden wpis zamiast siedmiu. Znika klasa błędów, gdzie walidacja UI rozjeżdża się z parsowaniem w CLI.

Komendy zamiast kombinacji flag

Dziś tryb wynika z --collect-metadata --assess-with-llm --scan-all-metadata --apply-assessment-decisions; jest nawet guard rzucający wyjątkiem przy złej kombinacji. Zamiast tego:

  • scholarone reject --dry-run | --send [--from-report=…]
  • scholarone screen --dry-run | --live
  • scholarone reviewers --prepare | --invite
  • scholarone doctor — preflight

Stare skrypty npm zostają jako aliasy.

doctor

Sprawdza Node, Chromium, codex login status, .env, miejsce na dysku. Dziś dowiadujesz się o wylogowanym Codexie po 10 minutach klikania.

5. UI — ~10 h

Strumień zamiast pollingu

SSE albo ?since=offset zamiast pobierania całych 120 KB co 1,5 s i przerysowywania <pre> od zera (scroll skacze). Procesy potomne emitują NDJSON obok czytelnego logu.

Realny postęp

Pasek 12/40, aktualny manuscript ID, decyzje na żywo, licznik APPROVE/REJECT/błędów, tokeny narastająco.

Wyniki screeningu w UI

Dziś zakładka potrafi odpalić run, ale nie pokazać wyników — są tylko w logs/screening/*-summary.csv. Dodaj tabelę + przycisk „wykonaj decyzje z tego przebiegu" (ten sam wzorzec co dry-run → reject z raportu).

Historia jobów

jobs to Map w pamięci — restart UI kasuje historię. Zapis do logs/jobs/<id>.json + link job → raport.

Odchudzenie frontu

app.js ma 692 linie i ręczną mapę 60+ elementów. Formularze renderowane z definicji opcji z etapu 4; jedna readForm(mode) zamiast sześciu funkcji *Options(); toasty zamiast alert().

6. Wydajność i koszt LLM — ~8 h

Rozdziel zbieranie od oceniania

Dziś: otwórz artykuł → skopiuj abstrakt → czekaj na LLM → następny. Dwa najwolniejsze zasoby stoją na przemian bezczynnie. Zamiast tego producent (przeglądarka) + pula 3–4 równoległych ocen połączone kolejką.

Czas runu spada do wolniejszego z etapów zamiast ich sumy.

Ocena wsadowa

Schemat batch już jest w repo i nie jest używany. N manuskryptów w jednym wywołaniu, dopasowanie wyników po manuscript ID, fallback na tryb pojedynczy. Prompt z regułami płacony raz na paczkę, nie raz na artykuł.

Cache ocen

Klucz: hash z manuscriptId + tytuł + abstrakt + prompt + model + reasoning effort. Flaga --no-cache wymusza świeżą ocenę.

Iterowanie nad promptem przestaje kosztować pełną stawkę przy każdej próbie.

Odetnij ocenę od CLI

llm-assessment.js jest zrośnięty z codex exec (flagi, parsowanie JSONL, --output-last-message, zliczanie tokenów ze zdarzeń). Wprowadź interfejs assess(manuscripts, options) z adapterami — obecny CLI plus opcjonalnie API po HTTP.

Decyzja: prompt-evals

scripts/evaluate-assessment-prompts.js + 1,7 MB w logs/prompt-evals/ to porzucona gałąź bez dokumentacji i bez wejścia z UI. Albo dociągnąć (zestaw referencyjny, raport dokładności), albo usunąć. Zostawienie jak jest to dług, który będzie mylił za pół roku.

7. Niezawodność — ~5 h

Wznawianie dla screeningu live

reject-from-report ma *.progress.json i pomija obsłużone manuskrypty. Screening live nie ma nic równoważnego — przy ponownym odpaleniu ryzykujesz powtórzenie akcji. Zapis stanu per ID przed akcją, domknięcie po potwierdzeniu.

Bezpiecznik na każdy tryb live

--max-rejected chroni auto-reject; screening live i zaproszenia nie mają odpowiednika, a --scan-all-metadata puszcza całą kolejkę.

Dziennik akcji

logs/actions.jsonl — czas, tryb, ID, akcja, wynik. Osobno od logów debugowych, więc nie podlega czyszczeniu z etapu 1. Odpowiada na „czy ten artykuł już dostał maila?" bez przekopywania 405 MB.

Rozbicie README

~300 linii mieszających instalację, trzy workflow i referencję flag; przykłady zdążyły się rozjechać ze skryptami npm. README = instalacja + pierwszy run + mapa trybów, reszta do docs/, a referencja flag generowana z definicji opcji z etapu 4.

Czego nie ruszać

  • Moduły reguł — manuscript-rules, reviewer-rules, screening-assessment, screening-batch. Czyste funkcje, dobrze pokryte. To wzorzec, do którego ma dojść reszta.
  • Wzorzec reviewer-selectors.js — rozszerzyć, nie zmieniać.
  • Podwójne potwierdzenia przed live — wygląda nadmiarowo, dopóki nie wyśle się przypadkiem 40 maili.
  • Weryfikacja skutku zamiast zamknięcia popupu — najlepszy fragment logiki reviewerów.
  • UI na 127.0.0.1 + kontrola Origin.
  • Reguła .R{n} i separacja dry-run od live — rdzeń modelu bezpieczeństwa.
