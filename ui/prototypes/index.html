UI prototypes

Five layouts for the same workflow: configure, dry run, review, execute. All use mock data. Dry-run buttons play a fake job for about 7 seconds so you can see how each layout shows a running job. Live buttons only show a confirm dialog.

  1. 1

    Desk

    Queue counts become the navigation. A left rail lists ScholarOne queues with the workflow that consumes each one underneath. A job dock sits at the bottom of every page and expands to show the log.

    Best if you want to see "how many are waiting" and "what to run" in one glance without a separate Queues tab.

    Open
  2. 2

    Routine

    One page, no tabs. Four stations in the order manuscripts move through ScholarOne. Each shows its queue count, last run, and the two buttons. Results expand inline. Settings live in a side drawer.

    Best for a daily pass: scan top to bottom, run what has a non-zero count.

    Open
  3. 3

    Workbench

    Two panes that fill the window. Left: workflow tabs and the form with the run buttons pinned at the bottom. Right: live log on top, results below. Nothing scrolls off screen. Keyboard: Alt+1..4 switch workflow, Cmd+Enter starts a dry run.

    Best if you watch the automation as it runs and want the log always visible.

    Open
  4. 4

    Ledger

    Runs are the main object. One chronological list of every run, each row showing how far it got on the path dry run, review, executed. Rows expand into results with the Execute button. New runs start from one menu that opens a drawer with the form.

    Best if the question you ask most often is "what did I run and what is still waiting for a decision".

    Open
  5. 5

    Guided

    A four-step path per workflow: Configure, Dry run, Review, Execute. One step on screen at a time. The Review step lets you override single decisions. The Execute step spells out exactly what will happen and needs a checkbox before the red button unlocks.

    Best if the priority is never sending anything by mistake, at the cost of more clicks.
